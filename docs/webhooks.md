# Webhook triggers

Webhook triggers accept JSON POSTs and start durable runs of a published workflow. The Rust/Wasm implementation works on Cloudflare and self-hosted workerd. New triggers default to **no authentication**; protection is an explicit choice.

## Configure an endpoint

1. Add/select a Webhook trigger, choose its authentication mode and save.
2. Choose **Generate endpoint**. For bearer/query authentication, copy the secret key shown once. Only its hash is stored; metadata reads never return it. If changing a public trigger to a protected one, rotate to obtain its new key before publishing.
3. Publish to activate that immutable definition. Pause or archive to stop new deliveries. Saving a draft preserves the live graph and authentication.
4. Send a JSON POST to the generated URL. No event ID is required.

```sh
curl --request POST "$WEBHOOK_URL" \
  --header 'Content-Type: application/json' \
  --data '{"orderId":"123","customer":"Ada"}'
```

Use the URL generated by your installation. Canonical URLs are `/hooks/<workspace-id>/<hook-id>`, outside the management API. Older `/api/hooks/<workspace-id>/<workflow-id>/<hook-id>` URLs remain direct aliases with the same authentication and lifecycle checks. No credential-bearing POST is redirected. Renaming does not change an endpoint; rotation immediately invalidates the old URL and key. A separate friendly workspace routing-key registry remains planned.

## Authentication modes

| `authentication` | Sender requirements |
| --- | --- |
| `none` | No credentials. The endpoint accepts public JSON events while active. |
| `bearer` | `Authorization: Bearer <generated-key>` |
| `query` | A single secret query parameter, named by `queryParameter` (default `key`), containing the generated key. Duplicate occurrences are rejected. |
| `hmac_sha256` | Timestamp/body signature described below; no event ID. |
| `hmac` | Legacy timestamp/event-ID/body signature, retained for existing senders. |

Examples of explicit trigger configuration:

```json
{"authentication":"query","queryParameter":"webhook_key"}
```

```json
{"authentication":"hmac_sha256","signingSecret":"incoming_webhook_key"}
```

A query-authenticated sender appends the generated key to the configured parameter. Keep secret-bearing URLs out of logs and workflow exports; bearer headers avoid putting credentials into URLs. Query authentication does not accept a bearer header as a substitute.

For HMAC modes, configure the named alias in the installation's `HTTP_SECRETS` JSON map using a Worker secret or a self-hosted secret mount. Send `X-Kasuri-Timestamp` as Unix seconds within five minutes of server time and `X-Kasuri-Signature` as lowercase HMAC-SHA256 hex (optionally prefixed with `sha256=`).

- `hmac_sha256` signs exact bytes of `timestamp + "." + rawRequestBody`.
- Legacy `hmac` signs `timestamp + "." + eventId + "." + rawRequestBody`, with `X-Kasuri-Event-Id` containing 1–128 ASCII letters, digits, dots, underscores or hyphens. That ID is part of this legacy signing format only; it does not deduplicate deliveries.

Signature checks bind the timestamp and payload and compare signatures in constant time. Provider-specific signature formats are not implemented. Neither HMAC mode accepts a bearer key as a fallback. Rotate named HMAC secrets independently from endpoint URLs.

## Delivery and retries

The accepted JSON value becomes workflow input directly. Authentication headers, consumed query credentials, signatures and cookies are not copied into run inputs. Use **Request Context** to read the immutable trigger body or selected metadata after other nodes transform the payload. Configurable methods/parsers/CORS remain planned.

A successful response is `202 Accepted`:

```json
{"runId":"opaque-run-id"}
```

Acceptance means the run is durably saved, not that every node succeeded. Inspect it in the dashboard/API. Every accepted delivery starts a distinct run, including identical payloads or repeated event IDs and deliveries after restart. The platform no longer requires event IDs or performs business-event deduplication; old delivery receipts are not consulted. If business rules need deduplication, claim a selected key with atomic `insert_if_absent` in Data Tables/Context Store and branch on its result before the protected effect. Do not reset real claims as the synthetic claim example does.

Engine effect recovery remains idempotent: recovering one persisted data task does not repeat its write. This is separate from deciding whether two incoming events represent the same business event. Timestamp windows limit signature age, but do not make repeated authenticated requests duplicates.

Payloads must be JSON and at most 32 KiB. Invalid credentials/signatures return `401`; inactive/rotated endpoints return `404`; unsupported methods/content types return `405`/`415`; oversized bodies return `413`; invalid JSON returns `400`. Active-run/checkpoint budgets still apply and can reject a delivery with `429`/`413`. Retry according to the workflow's business policy rather than assuming an event ID suppresses another run.

## Respond to Webhook

Response timing is expressed by node placement, with no async/sync switch on the trigger:

- **Webhook → process/validate → Respond to Webhook** returns the processing result.
- **Webhook → Respond to Webhook (202) → background work** acknowledges early, then continues the durable workflow.

A workflow containing a response node waits up to five seconds from acceptance. Workflows without one retain their immediate `202` acknowledgement. Different conditional branches can contain different response nodes; only the selected branch should respond. A second response attempt fails that node with `duplicate_response`; it does not overwrite or resend the original response. Future parallel races must select/join explicitly before one response node.

The response node sets `status` (default 200), `responseType` (`json` or `text`), optional `headers` and `body`. Bodies/header values support explicit `{"$input":"/pointer"}` references. JSON fields also accept JSON text from the editor. The node passes its input onward unchanged. Simulation and manual Run now produce a preview, including the proposed response in run details, without opening or submitting an HTTP response.

```json
{"status":201,"responseType":"json","headers":{"X-Result":"created"},"body":{"accepted":{"$input":"/accepted"}}}
```

Content type is generated from `responseType`. Bodyless statuses 204/205/304 require null or empty text. Response bodies/expansion are bounded to 32 KiB, with at most 16 headers and 8 KiB of header data. Cookies, hop-by-hop/framing headers and platform response headers cannot be set by workflows. The platform sets `Cache-Control: no-store`, `X-Content-Type-Options: nosniff` and `X-Kasuri-Run-Id` on synchronous responses.

The decision and run checkpoint commit before submission. Run details expose `webhookResponse`, including delivery state, deciding node, proposed response and whether the decision was late. Summary lists omit the response body. Delivery is separate from the workflow's final success/failure:

| Situation | HTTP result / recorded state |
| --- | --- |
| Response node reached in time | Configured response; `submitted` means attempted submission, not confirmed client receipt |
| Run succeeds on a path without a response | `502 workflow_completed_without_response`; `no_response` |
| Run fails/is cancelled before responding | `500 workflow_failed_before_response`; `failed` |
| Five-second window expires | `504 webhook_response_timeout`; `timed_out` |
| Caller disconnects before submission | `disconnected` when observed; otherwise a submission remains unconfirmed. No second response, and the durable run continues |
| Response node reached after timeout/disconnect | Decision recorded with `late: true`; no HTTP submission |

The response decision survives restart, but an interrupted HTTP connection cannot be reattached to a restarted process. An unsubmitted window closes at its deadline; a new delivery creates a new run. Client disconnects never cancel the workflow's independent alarms or effects. Transport cancellation may not reach the Durable Object before it prepares/submits a response; that case remains `submitted` without implying receipt. Native tests cover observed-abort transitions, and real TCP-disconnect tests verify independent workflow completion. The bounded responder uses Durable Object `waitUntil` for cleanup and forwards the incoming abort signal explicitly across the Worker/DO boundary. The configured compatibility date enables incoming `Request.signal`; see [Cloudflare's cancellation documentation](https://developers.cloudflare.com/workers/configuration/compatibility-flags/#enable-requestsignal-for-incoming-requests).

See [example 13](../examples/workflows/13-webhook-response.json), which previews without configuration and can be published on your own installation for a live `201` followed by background processing.

## Request Context

The Request Context node has a `part` setting:

| Part | Result |
| --- | --- |
| `metadata` (default) | `{ "trigger": "webhook", "request": { "method": "POST", "path": "/hooks/...", "headers": {}, "query": {} } }` |
| `body` | Original trigger input, unchanged by intermediate transforms |
| `headers` | Captured headers keyed by lowercase names |
| `query` | Captured query names mapped to arrays of values, preserving repeated parameters |

Webhook configuration chooses what is recorded. Default headers are `content-type` and optional `x-kasuri-event-id`; no query fields are recorded by default. To record selected business metadata:

```json
{"authentication":"none","contextHeaders":["content-type","x-business-event-id"],"contextQuery":["topic"]}
```

The editor also accepts these lists as JSON text. Header names are case-insensitive; query names are case-sensitive. Authorization/cookie/signature and credential-shaped names are excluded even if listed. A consumed query-auth parameter is always excluded, including custom names. Paths never contain the raw query string. Full incoming headers/URLs are not stored. Selected metadata is limited to 32 header/query names per list, eight values per query name, 4 KiB per value and 16 KiB total; over-budget selected values reject the delivery with `413` rather than silently truncating an event key.

Metadata is pinned in the run before execution and survives waits/restarts. Detailed run reads include the captured `context`; summary lists do not. This is request context, separate from persistent Context Store values. Manual/simulation/scheduled runs expose their trigger kind and `request: null`; header/query parts return empty objects, while `body` still reads their original input. Simulations never read ambient browser headers or production requests.

## Upgrade behavior

Existing stored triggers with omitted authentication retain their historical bearer default. Editing an existing trigger without an authentication field preserves its protection and related settings. To make it public, explicitly set `authentication: "none"`, save and publish. Existing explicit bearer/HMAC modes and token hashes remain valid. Draft edits never change live authentication.

All deployments adopt independent deliveries: the old automatic event-ID deduplication behavior is removed, including through legacy URL aliases. Consumers must use the returned run ID rather than the removed `eventId`/`duplicate` response fields.

## Management API and session protection

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/api/workflows/:id/webhook` | Read endpoint metadata/relative URL; no key |
| POST | `/api/workflows/:id/webhook/rotate` | Create/rotate endpoint; return a bearer/query key once when needed |
| POST | Generated `/hooks/...` URL | Deliver an external event under the published auth policy |

Management routes retain installation authentication, ownership/membership checks and CSRF protection. Producers need no management cookies or administrator password. A public routing ID is not a management capability. Keep the session-auth SQLite table with backups; sender-supplied management headers cannot grant access.

`pnpm test:runtime` covers public/bearer/query authentication, both HMAC formats, absent/repeated event IDs, independent deliveries across restart, immutable live auth, rotation, bounds, management-session isolation and Webhook → HTTP → Filter execution. No deployment IDs or private keys are shipped with the project.
