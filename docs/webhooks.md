# Authenticated webhook triggers

Webhook triggers accept external JSON events and start durable runs of published workflows. They are implemented in Rust/Wasm and work on Cloudflare and self-hosted workerd.

## Configure an endpoint

1. Add or select a Webhook trigger and save the workflow.
2. In the trigger inspector, choose **Generate endpoint and token**. Copy the POST URL and bearer token; the token is shown only in that response and is stored server-side as a hash.
3. Publish the workflow. Draft and paused workflows do not accept events.
4. Send an authenticated JSON POST with a unique `X-Kasuri-Event-Id`.

```sh
curl --request POST "$WEBHOOK_URL" \
  --header "Authorization: Bearer $WEBHOOK_TOKEN" \
  --header 'Content-Type: application/json' \
  --header 'X-Kasuri-Event-Id: order-123' \
  --data '{"orderId":"123","customer":"Ada"}'
```

Use the URL generated by your own installation. Authentication tokens must not be placed in URL query parameters or committed to workflow exports. Webhook credentials are separate from installation Basic authentication; producers do not need browser cookies or the installation administrator password.

The accepted JSON value becomes the workflow input directly. Authentication headers, signatures and cookies are not passed into node inputs or saved in run checkpoints. The resulting run has mode `webhook`.

A successful response is `202 Accepted`:

```json
{"runId":"opaque-run-id","eventId":"order-123","duplicate":false}
```

Acceptance means the run and deduplication record are durably saved, not that every node succeeded. Inspect the run in the UI/API for its final status. For example, Webhook → HTTP Request → Filter → Map / Transform can enrich and process an incoming event.

## Authentication and signatures

The default `authentication` setting is `bearer`. Generate/rotate the endpoint to obtain a fresh random token. Rotation immediately invalidates the old endpoint and token. Reading endpoint metadata never returns an existing token.

For signed events, set the trigger configuration to:

```json
{"authentication":"hmac","signingSecret":"incoming_webhook_key"}
```

Add `incoming_webhook_key` to the installation's `HTTP_SECRETS` JSON map using a Worker secret or a self-hosted environment/secret mount. Save and publish the updated workflow. In HMAC mode, bearer tokens are not accepted as an alternative. Endpoint rotation changes the URL; rotate the named signing secret separately when needed.

The sender must supply:

| Header | Value |
| --- | --- |
| `Content-Type` | `application/json` |
| `X-Kasuri-Event-Id` | Stable event ID for delivery retries |
| `X-Kasuri-Timestamp` | Unix timestamp in seconds, within five minutes of server time |
| `X-Kasuri-Signature` | Lowercase hex HMAC-SHA256, optionally prefixed with `sha256=` |

Sign the exact bytes of `timestamp + "." + eventId + "." + rawRequestBody`, using the named secret. Both the timestamp and event ID are authenticated along with the payload. Verification compares signatures in constant time and rejects stale/future timestamps outside the five-minute window.

This is Kasuri's generic signing format. Provider-specific formats such as GitHub, Slack and Stripe signature headers require their own adapters; they are not advertised as implemented here.

## Lifecycle, retries and limits

- Publishing/resuming enables deliveries. Pausing, or saving a new draft, disables them. A running workflow is not cancelled merely because its trigger is paused.
- Endpoint metadata reports the current activation state. Changing a trigger away from Webhook also disables its endpoint.
- Within a 24-hour window, the same endpoint and event ID with identical raw payload bytes returns the original run ID with `duplicate: true`, including after a restart. Reusing that ID with different bytes returns `409 Conflict`.
- Endpoint rotation starts a new deduplication scope. A replay after rotation or expiration can create a new run; inbound deduplication does not guarantee exactly-once external side effects.
- Event IDs contain 1–128 ASCII letters, digits, dots, underscores or hyphens. Payloads are JSON and at most 32 KiB.
- Up to 1,000 unexpired event records are retained per workspace. When full, delivery returns `429` instead of silently dropping replay protection. Active-run and checkpoint budgets also apply. Retry rejected deliveries using the same event ID/body; HMAC retries may use a fresh signed timestamp.
- Invalid credentials/signatures return `401`; inactive/rotated endpoints return `404`; unsupported content types return `415`; oversized bodies return `413`. Missing/invalid event IDs or JSON return `400`.

## Browser session protection

Management cookies contain a workspace routing ID plus an independent random session token, whose hash is stored separately in SQLite. Knowing the workspace routing ID present in a webhook URL does not authorize access to workflows or run history. Sender-supplied management headers are overwritten at the public Worker boundary.

Existing browser capabilities are upgraded on their next authorized management request. Keep the session-auth SQLite table when restoring backups. Versions predating this protection must not serve management requests for workspaces with exposed webhook routing IDs.

## API and verification

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/api/workflows/:id/webhook` | Read endpoint metadata and relative URL; no token |
| POST | `/api/workflows/:id/webhook/rotate` | Create/rotate the endpoint; return a bearer token once |
| POST | Generated `/api/hooks/...` URL | Deliver an authenticated external event |

Management routes retain installation authentication, workspace-session checks and cross-site request protection. The event route uses webhook authentication instead. No public deployment URLs, account IDs or webhook secrets are shipped in the repository.

`pnpm test:runtime` verifies bearer/HMAC authentication, tampered/expired signatures, restart-safe deduplication, rotation, activation/pause, size limits, management-session isolation and a real Webhook → HTTP → Filter run against a test upstream.
