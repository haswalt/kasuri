# Parallel branches and joins

Add **Split / Parallel** before independent branches. It passes input unchanged to outgoing success connections and explicitly enables parallel scheduling for that run. Select a concurrency bound of 2, 4 or 8; the default is 4. If a graph contains several split nodes, its smallest bound applies across the run. Existing graphs without a split retain their serial dispatch behavior and old single-slot checkpoints remain readable. Arrays stay single JSON values; this does not implicitly iterate items.

Add **Join** with at least two distinct parent nodes. Join waits until all incoming parents settle, then produces a stable object keyed by parent node ID. Connection order and HTTP completion order do not change those keys. Branch data remains independent; there is no shared mutable current payload.

- **all** returns outputs from active connections. An unhandled branch failure fails the run and prevents further dispatch. Explicit error outputs can still recover before a join.
- **collect** returns `{status, output}` for successful active parents, `{status:"failed", error:<safe code>}` for failed parents, and `{status:"skipped"}` for inactive parents. A failed node is collectable when all its outgoing connections lead directly to collect joins. For failures earlier in a multi-node branch, route its error output explicitly to a handler/final branch node. Unrelated unhandled errors still fail the run. A run may succeed while retaining a failed parent node in its trace because the join deliberately collected that error.

An entirely inactive join stays skipped. Each parent can connect once to a join; join policies never race multiple responses. IF still selects mutually exclusive paths. Deduplication claims and required validation gates belong **before** the split; running a claim alongside a protected write cannot prevent duplicates.

In-flight task IDs, dispatch markers and branch outcomes are persisted. Each HTTP result reloads the latest workspace and completes only its matching task, preserving sibling results and cancellation. Pause retains completed in-flight outcomes and prevents new dispatch; resume continues pending branches. Node retries repeat only the failed node, with its existing stable effect identity. Cancellation/fail-fast stops new work and ignores late results; it cannot undo an external write already sent. Restart does not blindly redispatch claimed HTTP effects: existing unknown-outcome/deadline rules remain in force.

The Rust host overlaps up to eight outbound HTTP futures per workspace alarm, within each run's selected concurrency bound. The same alarm driver advances earlier waits, retries and child completions while requests are outstanding. Data mutations remain synchronous SQLite transactions with durable receipts; they can progress alongside network branches, but database writes are not simultaneous transactions. Each simulated data effect remains isolated from live data, and simulation time is monotonic when sibling results complete out of order.

Runtime tests use a two-request rendezvous to prove actual overlap and verify that an early webhook response arrives while a slower HTTP branch is still running. Each/Loop, batching and richer merge adapters are separate future work.
